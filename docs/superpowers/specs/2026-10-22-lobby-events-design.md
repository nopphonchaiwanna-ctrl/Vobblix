# อีเวนต์ ส่วนที่ 2: หาอีเวนต์จากล็อบบี้ + วันเวลาเริ่ม + โต๊ะแข่งออนไลน์ — เอกสารออกแบบ

วันที่: 2026-10-22 · สถานะ: ผ่านผู้ตรวจแล้ว รอผู้ใช้อนุมัติ

"(ผู้ใช้)" = ผู้ใช้ตัดสินเอง · "(Claude)" = Claude ตัดสินแทน ผู้ใช้ค้านได้

## 1. เจตนา

ตอนนี้ผู้เล่นเห็นอีเวนต์ได้สองทาง คือเข้าไปในร้านแล้วเปิดบอร์ดอีเวนต์หรือเมนู HUD หรือกดปุ่ม "Events" ของแต่ละร้าน
ในรายการ "Published shops" ของล็อบบี้ ถ้าอยากรู้ว่า "ช่วงนี้มีงานอะไรบ้าง" ต้องไล่เปิดดูทีละร้าน
ส่วนที่ 2 ทำให้ผู้เล่น **เห็นอีเวนต์จากทุกร้านในที่เดียวบนล็อบบี้ ค้นหาได้ แล้วกดเข้าไปดูรายละเอียดหรือสมัครได้เลย** (ผู้ใช้)

สิ่งที่ผู้เล่นมีอยู่ในหัวตอนหางาน: **ชื่อร้าน, งานที่ใกล้จะถึง, การ์ดเกมอะไร** (ผู้ใช้)

หน้าล็อบบี้ยัง**ไม่ใช่ดีไซน์สุดท้าย** เพราะจะออกแบบใหม่ทั้งหน้าในภายหลัง (ผู้ใช้) รอบนี้จึงเน้นให้ใช้งานได้ครบ
และทำส่วนอีเวนต์เป็นชิ้นที่ยกไปวางที่อื่นได้ ไม่ผูกกับโครงล็อบบี้ตอนนี้ (Claude)

ระหว่างคุยกัน ผู้ใช้เจอปัญหาของส่วนที่ 1 อีกเรื่อง: งาน Swiss ที่ยาวหลายชั่วโมงหรือข้ามวันจะจองโต๊ะจริงในร้านไว้ทั้งงาน
(ระหว่างแข่ง คนนอกพูดหรือเปิดกล้องที่โต๊ะนั้นไม่ได้) พื้นที่เล่นการ์ดในร้านเลยใช้ไม่ได้ จึงรวมการแก้เรื่องนี้ไว้ในรอบนี้ด้วย (§5)

## 2. เป้าหมาย

1. อีเวนต์มี **วันและเวลาเริ่ม** ที่เจ้าของร้านใส่ตอนสร้าง ใส่แค่วันกับเวลาเริ่ม ไม่ต้องมีเวลาจบหรือช่องอื่น (ผู้ใช้)
2. **ถึงเวลาเริ่มแล้ว ระบบปิดรับสมัครเอง** แต่การเริ่มแข่งจริงยังรอผู้จัด approve การรายงานตัวให้ครบแล้วกดเริ่มเองเหมือนเดิม (ผู้ใช้)
3. ล็อบบี้มี **ส่วนอีเวนต์** ที่รวมงานจากทุกร้าน ค้นหาด้วยชื่อร้าน กรองด้วยเกมและช่วงเวลา แล้วกดเข้าไปดูรายละเอียดหรือสมัคร (ผู้ใช้)
4. **โต๊ะแข่งทุกงานเป็นโต๊ะออนไลน์** (โต๊ะพิเศษแบบเดียวกับโต๊ะที่ล้นตอนนี้) ไม่ใช้โต๊ะจริงในร้านเลย บังคับทุกงาน ผู้จัดไม่ต้องเลือก (ผู้ใช้)

## 3. ไม่อยู่ในขอบเขต

- เวลาจบงาน, คำอธิบายงาน, ค่าสมัคร, รางวัล (ผู้ใช้ให้ใส่แค่วันกับเวลาเริ่ม)
- แจ้งเตือนเตือนความจำก่อนงานเริ่ม (Claude: ไว้ทีหลังถ้าต้องการ)
- ระบบเปิด check-in หรือเริ่มแข่งเองตามเวลา (ผู้ใช้: ผู้จัดกดเองเหมือนเดิม)
- ดีไซน์ล็อบบี้ใหม่ทั้งหน้า (ผู้ใช้: ทำทีหลัง)
- ส่วนที่ 3 ประวัติการแข่ง และส่วนที่ 4 ส่งเด็ค/สถิติเด็ค
- i18n: ข้อความยังเป็นภาษาอังกฤษเหมือนส่วนอื่นของเว็บ (ตาม CLAUDE.md)

### หมายเหตุสำหรับส่วนที่ 4 (ผู้ใช้เพิ่งนึกได้)
แวนการ์ดฟอร์แมต **TH ยังไม่มีระบบ Deck Log** ถ้าส่วนที่ 4 บังคับส่งเด็คตอนสมัครหรือรายงานตัวผ่าน Deck Log
อีเวนต์ TH จะใช้งานไม่ได้ ส่วนที่ 4 ต้องมีวิธีส่งเด็คที่ไม่พึ่ง Deck Log สำหรับ `vanguard_region = 'th'`
เช่นพิมพ์หรือเลือกการ์ดจากแคตตาล็อก ให้ออกแบบรายละเอียดตอนทำส่วนนั้น
ส่วนที่ 2 ไม่กระทบเรื่องนี้ เพราะตอนนี้การสมัคร (`POST /events/:id/register`) ไม่มีเรื่องเด็คเลย และรอบนี้ก็ไม่เพิ่ม

## 4. วันเวลาเริ่ม

### 4.1 ข้อมูล
- migration ใหม่ `021_event_starts_at.sql`: `tournament_events.starts_at TIMESTAMPTZ NULL` + index ที่ช่วยค้นหาอีเวนต์ที่ใกล้จะถึง (Claude)
  ห้ามแก้ migration เก่า (CLAUDE.md)
- เก็บเป็น UTC แสดงตามเวลาเครื่องผู้ดู ซึ่งผู้ใช้ส่วนใหญ่อยู่ไทย (Claude)
- อีเวนต์เก่าที่มีอยู่แล้วมี `starts_at = NULL` ไม่ต้อง backfill (Claude) ผลคือไม่ปิดรับสมัครเอง และในรายการล็อบบี้
  จะอยู่ท้ายสุด ป้ายแสดงว่า "Date TBA"

### 4.2 ฟอร์มสร้าง/แก้อีเวนต์ (`client/src/ui/events/eventForm.js`)
- เพิ่มช่อง **Start date & time** (`<input type="datetime-local">`) และ**บังคับกรอกตอนสร้างงานใหม่** (Claude)
  ฝั่ง server ก็บังคับด้วย: `POST /events` ไม่มี `startsAt` ที่ถูกต้องให้ตอบ 400 (Claude)
- สร้างงานใหม่ต้องตั้งเวลาเป็นอนาคตเท่านั้น (Claude)
- ช่วง `registration` แก้ได้ทุกช่องเหมือนเดิม และเพิ่ม `startsAt`
- ช่วง `check_in` ตอนนี้มี **bug เดิม**: client ใช้ `basicsOnly = status !== "registration"` เลยแสดงฟอร์มชื่อกับเวลารอบ
  แต่ `PATCH /:id` ของ server ตอบ 409 ทุกครั้ง รอบนี้ให้แก้ด้วย: ช่วง `check_in` แก้ได้แค่ **ชื่อ, เวลารอบ, `startsAt`**
  ส่วน settings อื่นล็อกไว้ (Claude) client จึงมีฟอร์มสามแบบ: เต็ม (`registration`), พื้นฐาน + เวลาเริ่ม (`check_in`),
  พื้นฐาน (`swiss`/`bracket`)
- แก้งานเก่าที่ยังเป็น NULL ไม่บังคับให้ใส่ แต่ใส่ได้ (Claude)
- ถ้าผู้จัดเลื่อนเวลาไปอนาคตหลังจากที่ปิดรับไปแล้ว การรับสมัครจะเปิดอีกครั้งเอง เพราะเงื่อนไขปิดคำนวณจากเวลา (§4.3) (Claude)

### 4.3 ปิดรับสมัครเมื่อถึงเวลา
- ไม่มี cron หรือ job ใดๆ: ใน `POST /:id/register` ถ้า `starts_at IS NOT NULL AND now() >= starts_at`
  (ใช้นาฬิกาของ server ผ่านฟังก์ชัน pure ที่เทสต์ได้) ให้ตอบ 409 "Registration is closed for this event." (Claude)
- ปิดทั้งการสมัครใหม่และการต่อคิวสำรอง ทั้งในช่วง `registration` และ `check_in` (ผู้ใช้ยืนยัน)
- **ไม่เปลี่ยน status** ของงาน คนที่สมัครไว้แล้วยังรายงานตัว ถอนตัว หรือได้สิทธิ์จากคิวสำรองตามปกติ
  ผู้จัดยังกดสุ่ม เปิดรายงานตัว approve และเริ่มแข่งเองได้เหมือนเดิม ทั้งก่อนและหลังเวลาเริ่ม (ผู้ใช้)
- `GET /events/:id` และรายการอีเวนต์ส่ง `registrationOpen: boolean` ที่ server คำนวณมา
  เพื่อให้ client ซ่อนหรือปิดปุ่มสมัครพร้อมบอกว่า "Registration closed" โดยไม่ต้องเทียบนาฬิกาเครื่องเอง (Claude)
- หน้ารายละเอียดอีเวนต์ (ฝั่งผู้เล่นและผู้จัด) แสดงวันเวลาเริ่มบนหัวงานข้างป้ายเดิม (`badgesHtml`) (Claude)

## 5. โต๊ะแข่งเป็นโต๊ะออนไลน์ทั้งหมด

- `withTables()` และจุดที่เรียก `assignTables(..., physicalTables)` ตอนเริ่มงานใน `server/src/routes/tournaments.js`
  ให้ใช้จำนวนโต๊ะจริงเป็น **0 เสมอ** ทุกคู่จึงได้ `tableOnline: true` เลขโต๊ะยังเป็น 1, 2, 3… เรียงจากคู่คะแนนสูงเหมือนเดิม (ผู้ใช้)
  วิธีที่ง่ายที่สุดและอ่านแล้วตรงความหมายเป็นเรื่องของ builder เช่นเอา parameter ออกจาก `assignTables` แล้วแก้ comment หัวไฟล์ `tables.js`
- ผลที่ตามมาซึ่งต้องตรวจให้ครบ:
  - โต๊ะจริงในร้าน **ไม่ถูกล็อกผู้พูด** ระหว่างงานอีกต่อไป (`refreshEventTables`, `tournament/speakers.js`, `eventTables.js`,
    `client/src/webrtc/speakers.js`) ระบบล็อกผู้พูดยังทำงานกับโต๊ะออนไลน์เหมือนเดิม
  - "Go to table" และ "Watch" ใช้เส้นทางโต๊ะออนไลน์ที่มีอยู่แล้ว (`go-to-match` → `sitAt` ด้วย id `event:<eventId>:t<n>`)
    ผู้เล่นยังต้องเข้าร้านของงานก่อน (`ensureInShop`) เหมือนตอนนี้
  - ข้อจำกัดเดิมใน README ("สองงานพร้อมกันในร้านเดียวใช้เลขโต๊ะชนกัน") หายไป เพราะ id โต๊ะออนไลน์มี eventId อยู่แล้ว
    ให้ตรวจว่าจริงแล้วลบบรรทัดนั้นออก
  - งานที่กำลังแข่งอยู่ตอนอัปเดต: รอบที่จับคู่ไปแล้วเก็บเลขโต๊ะไว้แบบไหนให้คงไว้แบบนั้น รอบถัดไปเป็นออนไลน์ทั้งหมด
    ไม่ต้องย้ายข้อมูล (Claude: ตอนนี้ยังไม่ deploy จึงไม่มีงานจริงค้างอยู่)
- "รายงานตัวอัตโนมัติ" ยังดูจากคนที่อยู่ในร้าน 3D ของงานเหมือนเดิม ไม่เปลี่ยน (Claude)
- อัปเดตเทสต์ของ `tables.js` และ integration test ที่คาดว่าคู่บนจะได้โต๊ะในร้าน

## 6. ส่วนอีเวนต์ในล็อบบี้

### 6.1 Server: `GET /events/upcoming`
- ต้อง login เหมือน route อื่นใน router นี้ (Claude) และต้องลงทะเบียน route ก่อน `/:id`
- ส่งอีเวนต์จาก**ร้านที่ผู้เล่นทั่วไปเข้าได้** คือเกณฑ์เดียวกับรายการ Published shops (ร้านที่เผยแพร่แล้ว
  รวมร้าน central ของแอดมินถ้ารายการนั้นรวมด้วย) ใช้เงื่อนไขชุดเดียวกัน ไม่เขียนใหม่ให้ต่างกัน (Claude)
- สถานะที่แสดง: `registration`, `check_in` และงานที่กำลังแข่ง `swiss`, `bracket` (ติดป้าย "Live" ไว้ให้คนกดเข้าไปดูหรือ Watch ได้)
  ไม่แสดง `completed` และ `cancelled` (Claude)
- query params (ทั้งหมดไม่บังคับ) (Claude):
  - `q` ค้นหาแบบไม่สนตัวพิมพ์เล็กใหญ่ใน**ชื่อร้าน**และชื่องาน (ผู้ใช้บอกชื่อร้าน Claude เพิ่มชื่องานให้)
  - `game` ค่าจาก `GAME_LABELS` ฝั่ง client และ server ตรวจกับรายการเกมของตัวเอง (ใกล้ `tournaments.js:45`)
    ตอนนี้มีแค่ `vanguard` แต่ห้ามฮาร์ดโค้ดว่ามีเกมเดียว
  - `when` = `today` | `week` (7 วันข้างหน้า) | `all` (ค่าเริ่มต้น) งานที่กำลังแข่งผ่านทุกตัวกรองเวลา
    งานที่ยังไม่ระบุวันผ่านเฉพาะ `all` ส่วน "วันนี้" ใช้วันตามเวลาไทย (`Asia/Bangkok`) (Claude)
- **งานค้าง**: งานที่ยังไม่เริ่มแข่ง (`registration`/`check_in`) แต่เลยเวลาเริ่มมา**เกิน 24 ชั่วโมง** ไม่ต้องแสดงในล็อบบี้
  เพราะน่าจะถูกทิ้งไว้ ยังเปิดดูได้จากร้านเหมือนเดิม (Claude) งานที่เลยเวลาเริ่มไม่ถึง 24 ชั่วโมงยังแสดงอยู่
- ช่วงเวลา: `today` = ตั้งแต่ 00:00 ถึง 24:00 ของวันนี้ตามเวลาไทย, `week` = ตั้งแต่ 00:00 วันนี้ไปอีก 7 วัน
  งานที่เริ่มไปแล้วเมื่อเช้าวันนี้จึงยังอยู่ทั้งใน Today และ This week (Claude)
- เรียงลำดับ: งานที่กำลังแข่งก่อน ตามด้วยงานที่มีวันเริ่ม (ใกล้สุดก่อน) แล้วจึงเป็นงานที่ไม่ระบุวัน (ใหม่สุดก่อน) (Claude)
  งานที่เลยเวลาเริ่มแล้วแต่ยังไม่เริ่มแข่ง (กำลังรายงานตัว) ยังแสดงอยู่ แต่ `registrationOpen = false`
- จำกัด 50 รายการ ยังไม่มีแบ่งหน้า (Claude: ตอนนี้มีร้านไม่มาก)
- ข้อมูลแต่ละรายการ: id, ชื่องาน, game, vanguard region/regulation, `startsAt`, status, registration mode,
  จำนวนผู้เล่นที่ได้สิทธิ์ / `max_players`, ชื่อร้าน, code ร้าน, logo ร้าน, `registrationOpen`,
  และสถานะของผู้ดูเองในงานนั้น เพื่อแสดงป้าย (Claude): `entered` → "Registered", `pending_draw` → "Entered draw",
  `waitlisted` → "Waitlist #N", ส่วน dropped/no-show/ไม่ได้สมัคร → ไม่มีป้าย
  ใช้ `publicEvent` เดิมเป็นฐาน ห้ามส่ง field ที่หน้า by-shop ไม่ส่ง
- query นี้ต้องไม่ช้าเมื่อมีอีเวนต์เยอะ ให้ใช้ query เดียวที่ join ร้านและนับผู้เล่นเอง ไม่ยิงซ้ำทีละงาน

### 6.2 Client: โมดูลแยก `client/src/ui/lobbyEvents.js`

  และป้ายสถานะของผู้ดูเอง (§6.1)
- กดแถว → `navigate("/events/<id>")` เปิดหน้ารายละเอียดเดิม ซึ่งมีปุ่มสมัครอยู่แล้ว (route `/events/:eventId` ใน `main.js`)
  ไม่ต้องสร้างหน้ารายละเอียดใหม่ (Claude) ปุ่ม Back ของหน้านั้นต้องกลับมาที่ล็อบบี้พร้อมตัวกรองเดิม
  (เก็บตัวกรองไว้ในโมดูล ไม่ต้องเก็บลง URL) (Claude)
- ตอนโหลด, ไม่มีผลลัพธ์ ("No events match - try another shop name or All dates") และตอน error ต้องมีข้อความบอกทุกกรณี
- รีเฟรชรายการทุกครั้งที่กลับเข้าล็อบบี้ (ผูกกับ `refreshLobbyExtras()`) ไม่ต้องอัปเดตแบบ live (Claude)
- ปุ่ม "Events" รายร้านใน Published shops ยังอยู่เหมือนเดิม (Claude)
- ใช้งานบนมือถือแนวนอนได้ ตัวควบคุมขึ้นบรรทัดใหม่ได้ และไม่มี scroll แนวนอน

## 7. เทสต์และการตรวจ

- Server: unit test สำหรับ logic ที่แยกออกมาได้ เช่นการตัดสินว่าเปิดรับสมัครหรือยัง และ `assignTables` ที่เป็นออนไลน์ทั้งหมด
