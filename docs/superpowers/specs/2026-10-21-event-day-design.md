# อีเวนต์ ส่วนที่ 1: วันงาน (สมัคร → รายงานตัว → แข่ง) — เอกสารออกแบบ

วันที่: 2026-10-21 · สถานะ: ผ่านผู้ตรวจแล้ว รอผู้ใช้อนุมัติ

"(ผู้ใช้)" = ผู้ใช้ตัดสินเอง · "(Claude)" = Claude ตัดสินแทน ผู้ใช้ค้านได้

## 1. เจตนา

หน้าอีเวนต์ตอนนี้ (`client/src/ui/eventsPanel.js`) ทำงานได้ครบในเชิงระบบ (Swiss + top cut, จับเวลารอบ,
รายงานผลสองฝั่ง + override) แต่ **UI ไม่เป็นสัดส่วน ทุกอย่างเรียงยาวหน้าเดียว และหน้าจัดอีเวนต์ยังมีเมนูขาด** (ผู้ใช้)
เทียบกับระบบจริง (Bushi Navi, Bandai TCG+, Play! Pokémon) สิ่งที่ขาดคือ "ประสบการณ์วันงาน":
รายงานตัว, เลขโต๊ะ, แจ้งเตือนคู่รอบใหม่, เรียกกรรมการ

จุดที่เราเหนือกว่า: ร้านเป็นพื้นที่ 3D จริง — เลขโต๊ะพาไปนั่งโต๊ะในร้าน + call ได้ทันที, และรู้ว่าใคร "อยู่ในร้าน"
จึงรายงานตัวอัตโนมัติได้

งานอีเวนต์ทั้งหมดแบ่ง 4 ส่วน ทำทีละส่วน (ผู้ใช้เห็นด้วย): **1. วันงาน (เอกสารนี้)** · 2. แดชบอร์ดหาอีเวนต์ในล็อบบี้ + ค้นหา ·
3. ประวัติการแข่งของผู้เล่น · 4. ส่งเด็ค + สถิติเด็ค Vanguard
ส่วนที่ 1 ทำทั้งฝั่งผู้เล่นและผู้จัดพร้อมกัน (ผู้ใช้)

## 2. เป้าหมาย

### 2.1 ตั้งค่าอีเวนต์
- **วิธีสมัคร** ผู้จัดเลือกตอนสร้าง: **ใครมาก่อนได้ก่อน** หรือ **สุ่ม** (ผู้ใช้)
- **Vanguard**: เลือก **TH / JP** และ **Premium / D-Standard** (ผู้ใช้) — บังคับกรอกเมื่อ `game = vanguard` (Claude)
  เกมอื่นไม่มีช่องนี้ (ผู้ใช้) แสดงเป็นป้ายบนหัวอีเวนต์
- แก้ได้เฉพาะช่วงรับสมัคร เหมือนการแก้ settings เดิม (Claude)

### 2.2 สมัคร + คิวรอ
- ใครมาก่อนได้ก่อน: เต็ม `max_players` แล้ว คนถัดไปเข้า **คิวรอ** ตามลำดับเวลาสมัคร (ผู้ใช้)
- สุ่ม: ระหว่างรับสมัคร ทุกคนเป็น "สมัครแล้ว (รอสุ่ม)"; **ผู้จัดกดปุ่มสุ่มเอง** (ผู้ใช้) → สุ่มเลือก `max_players` คน
  ที่เหลือเข้าคิวรอตามลำดับที่สุ่มได้ (ผู้ใช้: ไม่ได้รับเลือกเข้าคิวรอ) — แบบสุ่มต้องตั้ง `max_players` (Claude)
  สมัครหลังสุ่มแล้ว → ต่อท้ายคิวรอ (Claude)
- มีคนถอน (ก่อนเริ่มแข่ง) → คนแรกในคิวได้สิทธิ์แทน อัตโนมัติ + ได้แจ้งเตือน (ผู้ใช้/Claude) หลังเริ่มแข่งไม่เลื่อนคิว (Claude)
- ผู้เล่นเห็นสถานะตัวเองชัด: สมัครแล้ว / รอสุ่ม / ได้สิทธิ์ / คิวรอที่ N / ไม่ได้รับเลือก

### 2.3 รายงานตัว (check-in)
- ผู้จัดกด **"เปิดรายงานตัว"** เอง (ผู้ใช้) → อีเวนต์เข้าสถานะใหม่ `check_in` (Claude)
- ผู้เล่นกด "รายงานตัว" → รอ **ผู้จัด approve** (ผู้ใช้) ผู้จัด approve ทีละคนได้
- ปุ่ม **"รายงานตัวอัตโนมัติ"**: approve ทุกคนที่ได้สิทธิ์ และ **ตอนนี้อยู่ในร้าน 3D ของอีเวนต์นั้น** (ผู้ใช้) —
  ใช้ presence เดิมใน `server/src/rooms.js` (จับคู่ด้วย `userId` ในห้องที่ code = ร้านของอีเวนต์) ไม่ต้องกดรายงานตัวเองก่อน (Claude)
- **"เริ่มแข่ง"** กดได้เฉพาะช่วง `check_in` และจับคู่**เฉพาะคนที่ approve แล้ว** (Claude ตามที่ผู้ใช้ยืนยันว่ารายงานตัวเป็นด่านเข้าแข่ง)
  คนที่ได้สิทธิ์แต่ไม่ approve → บันทึกเป็น "ไม่มา" (ไม่นับว่าถอนเอง)
- **คิวรอเติมที่ว่างของคนไม่มา** (ผู้ใช้): คนในคิวรอรายงานตัวได้ (แสดงเป็น "คิวรอ"); ผู้จัด approve ได้ และ "รายงานตัวอัตโนมัติ"
  ครอบคลุมคนในคิวรอที่อยู่ในร้านด้วย ตอนกด "เริ่มแข่ง" ถ้าคนที่ได้สิทธิ์และ approve แล้วยังไม่ถึง `max_players`
  ระบบดึงคนในคิวรอที่ approve แล้วมาเติมตามลำดับคิวจนเต็ม (ไม่มี `max_players` = ไม่มีคิวรอ ทุกคนที่ approve ได้แข่ง)

### 2.4 แจ้งเตือน
- **ขอ consent ทุกอีเวนต์** ตอนผู้เล่นกดรายงานตัว (ผู้ใช้ให้ขอก่อนเริ่มทุกงาน; Claude เลือกจังหวะ) — ปฏิเสธได้ แข่งต่อได้ตามปกติ
- ได้ consent → ลงทะเบียน **Web Push** (service worker + VAPID) เด้งเข้าเครื่องแม้ปิดเว็บ (ผู้ใช้)
- **iPhone**: ตอนขอ consent ถ้าเป็น iOS Safari ที่ยังไม่ได้ "เพิ่มไปหน้าจอโฮม" ขึ้นคำแนะนำวิธีเพิ่ม (ผู้ใช้) — iOS ส่ง Web Push ได้เฉพาะเว็บที่ติดตั้งเป็นแอป
- ผู้จัดกด **"ส่งแจ้งเตือนคู่รอบนี้"** (ผู้ใช้) → แต่ละคนได้ข้อความเฉพาะตัว เช่น "รอบ 2: โต๊ะ 3 vs MaohSan" ทั้งในกระดิ่งแจ้งเตือนเดิม (`notifications`) และ push (ถ้า consent)
- แจ้งเตือนเรื่องอื่นที่ส่งอัตโนมัติ (Claude): ได้สิทธิ์จากคิวรอ, ผลสุ่ม, เรียกกรรมการ (ถึงผู้จัด/กรรมการ), บทลงโทษ

### 2.5 ระหว่างแข่ง: คู่ + เลขโต๊ะ
- **ไฮไลต์คู่ของผู้ใช้** ในรายการคู่ (ผู้ใช้)
- **เลขโต๊ะ 1, 2, 3…** (ผู้ใช้) ทุกรอบทั้ง Swiss และ bracket; bye ไม่มีโต๊ะ
- โต๊ะ 1..N = โต๊ะในร้าน 3D ตามลำดับ `TABLES` ของร้าน; คู่ที่เกิน N ได้ **โต๊ะออนไลน์** เลขต่อเนื่อง N+1… (ผู้ใช้: แบบ A)
- แจกโต๊ะในร้านให้คู่ **อันดับสูงก่อน** (คะแนนรวมสองคน) แบบ "โต๊ะถ่ายทอด" (Claude)
- ปุ่ม **"ไปที่โต๊ะ"** บนการ์ดแมตช์:
  - โต๊ะในร้าน: ถ้ายังไม่ได้อยู่ในร้านนั้น → เข้าร้านก่อน; แล้ววาร์ปตัวละครไปข้างโต๊ะ + เข้าโหมดนั่งโต๊ะ + เข้า call (เหมือนกด "Join table") (Claude)
  - โต๊ะออนไลน์: เข้าโหมดนั่งโต๊ะ (C1 + แชทโต๊ะ) ได้ทันทีแม้ไม่มีโต๊ะในฉาก ต้องอยู่ในร้านของอีเวนต์ (เข้าให้อัตโนมัติ) (Claude)
  - ใครเข้าโต๊ะออนไลน์ได้: ผู้แข่งของโต๊ะนั้น, ผู้จัด, กรรมการ — และ **คนทั่วไปเข้าดูได้เป็นผู้ชม** (ผู้ใช้)
    ผ่านปุ่ม **"ดู"** ในแถวโต๊ะออนไลน์ของรายการคู่ ได้ยิน/เห็น แต่ไมค์/กล้องปิด เหมือนผู้ชมโต๊ะในร้าน (§2.6)
    ใช้เพดานผู้ชมเดียวกัน (8) และต้องอยู่ในร้านของอีเวนต์ (เข้าให้อัตโนมัติ) (Claude)
- รายงานผล: ใช้ระบบเดิม (ผู้ใช้)

### 2.6 ล็อกไมค์/กล้องที่โต๊ะแข่ง
- ระหว่างรอบ โต๊ะที่มีแมตช์อยู่ (ในร้านหรือออนไลน์): **ใช้ไมค์/กล้องได้เฉพาะผู้แข่งสองคนของโต๊ะ + ผู้จัด + กรรมการ** (ผู้ใช้)
- คนอื่นนั่งดูได้เป็น **ผู้ชม** — ได้ยิน/เห็น แต่ไมค์/กล้องปิด; แชทโต๊ะพิมพ์ได้ (Claude)
- คนที่นั่งอยู่ก่อนรอบเริ่ม → ถูกปิดไมค์/กล้องอัตโนมัติ + ข้อความ "โต๊ะนี้ใช้แข่งอยู่" (Claude)
- บังคับสองชั้น เพราะ call เป็น mesh: server ไม่อนุญาต `enable-video` / ส่งสถานะผู้พูดได้, และ**เครื่องผู้แข่งไม่เล่นเสียง/ภาพจากคนที่ไม่มีสิทธิ์**ตามรายชื่อจาก server (Claude)
- ล็อกหมดเมื่อรอบนั้นจบ (สร้างรอบใหม่ / อีเวนต์จบ / ยกเลิก)
- เพดานเดิมยังใช้: voice ≤10 (นับผู้ชมด้วย), video ≤4

### 2.7 กรรมการ + เรียกกรรมการ + บทลงโทษ (ผู้ใช้เสนอ)
- ผู้จัด **เพิ่มกรรมการ** รายอีเวนต์ ค้นจากชื่อบัญชี (Claude: ค้นจาก display name, ≥2 ตัวอักษร, ได้ไม่เกิน 10 ชื่อ)
- กรรมการ: ใช้ไมค์/กล้องได้ทุกโต๊ะแข่ง + ได้แจ้งเตือนเรียกกรรมการ (ผู้ใช้) — **แก้ผลแมตช์ไม่ได้** (ผู้ใช้)
- ผู้เล่นกด **"เรียกกรรมการ"** บนการ์ดแมตช์ระหว่างรอบ → ผู้จัด+กรรมการทุกคนได้แจ้งเตือน "โต๊ะ 3 เรียกกรรมการ" พร้อมปุ่ม "ไปที่โต๊ะ" (ผู้ใช้/Claude)
  - ผู้เล่นเห็น "เรียกแล้ว รอกรรมการ"; เรียกซ้ำได้หลัง 60 วินาที (Claude)
  - กรรมการคนแรกกด "รับเรื่อง" → หายจากคิวของคนอื่น; ปิดเรื่องเมื่อเสร็จ (Claude)
- **บทลงโทษ** (ผู้ใช้: มีระบบคาดโทษ) 3 ระดับ + เหตุผลบังคับ (Claude):
  - ตักเตือน — บันทึกทันที
  - แพ้แมตช์นี้ / ตัดสิทธิ์ — ถ้ากรรมการออก: "รอผู้จัดยืนยัน"; ผู้จัดยืนยัน → ระบบเปลี่ยนผลแมตช์ (แพ้) / ถอนผู้เล่น + แพ้แมตช์ปัจจุบัน ถ้าผู้จัดออกเอง: มีผลทันที
  - ผู้ถูกลงโทษ ผู้จัด และกรรมการเห็น; ส่วนที่ 3 จะแสดงในประวัติ

### 2.8 UI
- **มุมผู้เล่น: แดชบอร์ด 2 คอลัมน์** (ผู้ใช้ เลือกแบบ B จาก mockup) — ซ้าย: ข้อมูลอีเวนต์ + ป้าย (เกม, TH/JP, Premium/D-Std, จำนวนคน) + ขั้นตอนแนวตั้ง; ขวา: การ์ด "สิ่งที่คุณต้องทำตอนนี้" (สมัคร / รายงานตัว / แมตช์ของคุณ: โต๊ะ, คู่แข่ง, เวลาที่เหลือ, ไปที่โต๊ะ, รายงานผล, เรียกกรรมการ) แล้วตามด้วยรายการคู่รอบนี้ / ตารางคะแนน / ผู้เล่น
  มือถือพับเป็นคอลัมน์เดียว (Claude)
- **มุมผู้จัด: แถบขั้นตอน + แถบปุ่ม + แท็บ** (ผู้ใช้ เลือกแบบ A) — แถบขั้นตอน (สมัคร → รายงานตัว → Swiss n/N → Top X → จบ), แถบปุ่มเปลี่ยนตามขั้น
  (สุ่ม / เปิดรายงานตัว / รายงานตัวอัตโนมัติ (จำนวนคนในร้าน) / เริ่มแข่ง (จำนวนที่ approve) / ส่งแจ้งเตือน / รอบถัดไป / ⋯ แก้ไข·ยกเลิก),
  แท็บ: รายงานตัว · คิวรอ · คู่รอบนี้ (override เดิม) · เรียกกรรมการ (+ตัวเลข) · บทลงโทษ · กรรมการ · ผู้เล่น
- กรรมการเห็นมุมผู้จัดแบบลดสิทธิ์: แท็บคู่รอบนี้ (ไม่มี override), เรียกกรรมการ, บทลงโทษ (Claude)
- ข้อความ UI เป็นภาษาอังกฤษเหมือนส่วนอื่นของแอป (i18n ยังไม่ทำ) (Claude)
- เปิดจากที่เดิมได้ทั้งหมด (บอร์ดอีเวนต์ในร้าน, เมนู ⊞, ลิงก์แจ้งเตือน `/events/:id`) เป็นแผงซ้อนบนร้านตาม `ui/screens.js`

### 2.9 คำตัดสินเพิ่มหลังผู้ตรวจอ่าน (Claude ทั้งหมด ค้านได้)
- **push ของผู้จัด/กรรมการ:** ขอ consent ตอนผู้จัดกด "เปิดรายงานตัว" และตอนกรรมการเปิดหน้าอีเวนต์ครั้งแรกหลังถูกเพิ่ม
  เก็บ consent เป็นรายผู้ใช้ต่ออีเวนต์ ไม่ขึ้นกับบทบาท
- **แบบสุ่ม:** ปุ่ม "เปิดรายงานตัว" กดได้หลังสุ่มแล้วเท่านั้น (สองขั้น เห็นผลสุ่มก่อน)
- **รับสมัครปิดเมื่อเปิดรายงานตัว** ยกเว้นการต่อคิวรอ (ดู §2.3 เรื่องเติมที่ว่าง)
- **"แพ้แมตช์" ใช้ได้กับแมตช์ของรอบปัจจุบันเท่านั้น** (ยังไม่ได้สร้างรอบถัดไป) ถ้ารอบถัดไปจับคู่ไปแล้ว ระบบไม่ให้เลือกระดับนี้
  เหลือแค่ตักเตือน/ตัดสิทธิ์ (ตัดสิทธิ์ = ถอนจากรอบถัดไป ไม่ย้อนแก้ผลเก่า) — ไม่ย้อนเวลาใน swiss.js/bracket.js
  ทุกอีเวนต์ตอนนี้เป็นแมตช์เดียว (Bo1) "แพ้แมตช์" จึงหมายถึงแพ้แมตช์นั้นทั้งแมตช์
- **เพดานเสียง 10 คนที่โต๊ะแข่ง:** กันที่ไว้ 2 ที่สำหรับผู้แข่งสองคน — ผู้ชมเข้าได้ถึง 8; ผู้จัด/กรรมการเข้าได้เสมอ (เพดานแข็ง 12)
- **กรรมการแข่งในอีเวนต์เดียวกันไม่ได้** — เพิ่มคนที่สมัครอยู่เป็นกรรมการไม่ได้ และกรรมการสมัครไม่ได้

## 3. ไม่อยู่ในส่วนนี้
- แดชบอร์ดหาอีเวนต์ + ค้นหา (ส่วนที่ 2), ประวัติการแข่ง (ส่วนที่ 3), ส่งเด็ค + สถิติเด็ค (ส่วนที่ 4: สถิติรายอีเวนต์เจ้าของร้านดูได้, รวมทุกอีเวนต์ admin เท่านั้น — ผู้ใช้)
- ไม่เปลี่ยนวิธีจับคู่ Swiss / bracket / คิดคะแนน
- ไม่มีค่าสมัคร/ชำระเงิน, ไม่มี SMS

## 4. ข้อห้าม
- ห้ามให้กรรมการแก้ผลแมตช์
- ห้ามส่ง push โดยไม่มี consent ของอีเวนต์นั้น
- ห้ามให้คนนอกพูด/เปิดกล้องในโต๊ะแข่งได้ แม้จะแก้ client
- ห้ามให้ผู้เล่นที่ยังไม่ approve ถูกจับคู่

## 5. ข้อจำกัด / ข้อกำหนดโปรเจกต์
- migration ใหม่ต่อจาก 019 ห้ามแก้ของเก่า; server ทุกพฤติกรรมใหม่มี test (`npm run test:all`), client logic ใหม่ที่เป็น pure function มี `node:test`
- Web Push: ต้องมี VAPID keys ใน env (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`) — เพิ่มใน `render.yaml` (sync:false) และ `docs/deploy.md`; ไม่มีค่า → ระบบยังทำงาน แค่ไม่ส่ง push (แจ้งเตือนในเว็บยังมี)
- อย่าสมมติว่ามีแต่ Vanguard; ฟิลด์ TH/JP · Premium/D-Std ผูกกับ `game = vanguard`
- ใช้ `confirmDialog()` / `<dialog>`; เคารพ `prefers-reduced-motion`

## 6. ปล่อยให้ผู้ลงมือตัดสิน
- รายละเอียด schema (ชื่อตาราง/คอลัมน์), รูปแบบ API, การแยกไฟล์ `eventsPanel.js`
- ไลบรารี Web Push ฝั่ง server (เช่น `web-push`) และโครง service worker
- id ภายในของโต๊ะออนไลน์ใน socket layer
- วิธีวาร์ปตัวละครไปข้างโต๊ะ (ต้องผ่าน range check เดิม)
