# Event Day (Part 1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give events a real event-day flow:
- registration modes (first-come or lottery) with a waitlist, and Vanguard TH/JP + Premium/D-Standard settings
- check-in with organizer approval, plus auto check-in for players present in the shop
- table numbers (in-shop tables, then online tables), with spectating and per-round mic/camera locks
- judges, judge calls, and penalties
- Web Push with per-event consent
- a redesigned event UI (player view = 2-column dashboard, organizer view = stepper + action bar + tabs)

**Architecture:** The rules are pure, unit-tested modules under `server/src/tournament/`:
- `entry.js` handles entry, lottery, waitlist and fill.
- `tables.js` handles table assignment.
- `speakers.js` handles speaker rights.

The REST routes in `server/src/routes/tournaments.js` (plus a new `routes/judging.js`) persist state through `server/src/db/tournaments.js`. The socket layer (`server/src/index.js`) reads each shop's active event tables for online-table joins and the mic lock. On the client, `ui/eventsPanel.js` is split into a view per role. Web Push uses a service worker at `client/public/sw.js` and the `web-push` package on the server.

**Tech Stack:** Node 22, Express, Socket.io, Postgres (`pg`), `web-push`, vanilla JS + Vite, node:test.

**Spec:** `docs/superpowers/specs/2026-10-21-event-day-design.md` (Thai; binding)

## Global Constraints

- New migration `020_event_day.sql`. Never edit 001–019.
- Server: every new behavior has a test. Run `cd server && npm run test:all` before calling it done.
- Client: pure logic is tested with `cd client && npm test`. Also run `npm run build` and `node --check` on every touched file.
- UI copy is English (no i18n yet). Use `confirmDialog()` / `<dialog>`, never `window.confirm`/`prompt`. Respect `prefers-reduced-motion`.
- Vanguard-only fields (`vanguardRegion` ∈ `th|jp`, `vanguardRegulation` ∈ `premium|d_standard`) are required when `game === "vanguard"` and must be null for any other game.
- Judges can never override results. Push is only sent to a user who consented **for that event**.
- At a table in a running match, only the 2 players + the organizer + judges may speak or show video. This is enforced on the server AND by the players' clients refusing non-speakers' media.
- Voice cap at a match table: spectators ≤ 8. Players always get a seat. Staff can always join (hard cap 12). Video ≤ 4 as before.
- Re-call cooldown for "Call judge": 60 s per match.
- `"Match loss"` penalties are only allowed on a match of the **current** round (not after the next round is paired). DQ = drop from future rounds, never rewrite past results.
- Push needs `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`. With none set, everything works and push is silently skipped.
- Commit one task at a time on `dev` (the user approved per-task commits on this branch). Don't push without asking.

## Review Focus

1. **Organizer actions racing each other.** Examples: two organizer tabs both press Start or Draw; a player drops while auto check-in runs. The expected behavior is one effect, with the second call getting a 409 and no duplicate rounds or double promotions. → Task 4/5 integration tests "start twice → one round 1" and "draw twice → 409".
2. **A player who is both on the waitlist and checked in when spots free up.** They must be promoted in queue order, and nobody past `maxPlayers` gets paired. → Task 2 unit test "fill never exceeds max and keeps queue order", plus a Task 5 integration test.
3. **Someone who isn't a speaker forging mic or video at a locked table.** Their `enable-video` gets refused, and the players' clients drop that peer's audio. → Task 7 socket test, plus the Task 12 unit test `shouldPlayPeerMedia`.
4. **A judge call or penalty on a match that has just finished, or for an event the user isn't staff on.** Expect a 409 or 403 respectively, never a silent success. → Task 8 and Task 9 tests.
5. **Push with no VAPID keys, or an expired subscription (HTTP 410).** In-app notifications still go out; dead subscriptions are deleted. → Task 10 unit test using a fake sender.
